## 0. Verdict in six lines

1. `setComputeDevice(.cpu/.gpu, for: .main)` on VNRecognizeTextRequest rev3 is accepted and IGNORED: same ANE traffic (234 vs 234 executions per 13 reads), cold compile not avoided (89 s CPU-first, 64 s GPU-first). CPU/GPU fallback is not a lever. `.fast` is the only ANE-free path (supported devices = [cpu]; 0 ANE opens; 0.06 s per read), Latin only.
2. All VNRecognizeTextRequest performs of ONE process are serialized (accurate 3.7-4.0 reads/s whether 1 or 16 threads; `.fast` also waits behind a running accurate read: worst 0.68-0.76 s against 0.06 s idle). Another process is not affected (two processes: 3.27 reads/s each against 3.58 alone; one process sat 138 s in a cold compile while the other kept reading at full speed). So ONE stuck/slow request blocks document, rev3 and fast of the same process: that is the shape of the "all three did not answer in 8 s" symptom.
3. `VNRequest.cancel()` works on warm requests: queued requests leave the queue at once (5 queued reads returned `ERR 1` at 0.61 s instead of 1.2-3.6 s), a running read aborts (0.19 s instead of 0.6 s) and the next read is normal. The app never cancels (abandoned reads keep running and keep the serialized queue busy). Cancel during a cold compile is NOT measured.
4. Request / handler reuse changes nothing (identical counts). Device open (~1), program map+unmap (~5+5) and ANE executions (~18) happen per read: 243 opens and 1009 map/unmap in 9 min is ~200 reads = normal traffic, not a symptom. Vision keeps no program resident between requests.
5. This Mac's own log shows a process (pid 11524, `Mwoyeo.debug.dylib`) stuck for 2 h 57 min in `e5rt ... create_precompiled_compute_operation_with_options call failed (Code: 13)`: 13,361 errors from 13:24:16 to 16:21:16, it began right after `rev3 did not answer in 8 s` (13:23:57) and `fast OCR failed: Timeout()` (13:24:13); only a restart ended it (new pid 16567 is healthy). "programs not ready" is not always transient.
6. Next probe only with the lead's go (about 2 min of ANE compile): cancel() of a request that waits for a cold compile (does perform return, does the compile continue, does the next read start over).

## 6. Q3: how Vision uses the ANE (known / unknown)

Measured here: per read ~1 device open, ~5 map + ~5 unmap, ~18 executions (one per text-line batch); programs unmap at the end of each request (no residency between requests); the compile cache is per binary/bundle (fresh path or copy = cold; same-path rebuild of a bare binary stayed warm 6/6); a program is compiled per text-line width class (ocr-vn round) and each new class costs 30-60+ s of ANECompilerService CPU; rev2 and rev3 both use the ANE, `.fast` never.
Outside:
- Apple (WWDC22 10027 https://developer.apple.com/videos/play/wwdc2022/10027/): load once and hold the model ("loading the model prior to each prediction is generally not good practice"); nothing about ANE compile cache, eviction, idle unload, concurrency or per-process limits in any Apple talk read (WWDC22 10027, WWDC23 10047, WWDC24 10163, WWDC25 272).
- Apple DTS (forum 784672, 850058): the ANE is the resource constraint under parallel Vision requests; failed compiles are not cached; "iOS 27.2 beta 4 improves first-load".
- Community reverse engineering (NOT Apple, unverified): aneforge FAQ https://aneforge.readthedocs.io/en/latest/faq/ "`aned` keys its HWX cache by PID", "You can copy the on-disk compile artifacts, but they won't load in a different process"; e5rt dispatch reference https://aneforge.readthedocs.io/en/latest/e5rt-dispatch-reference/ "~128 loaded programs per PID (the 129th load fails; release() frees a slot)", "in-flight depth is capped at 127", "A bundle compiled elsewhere fails with 'ANE model load has failed ... Must re-compile the E5 bundle'"; Orion paper (arXiv 2603.06728, https://www.alphaxiv.org/abs/2603.06728.md, S) "~119 compilations per process limit ... Silent fail / crash", workaround exec() restart; ANE evaluation queue depth 127, hard power gating when idle (S). Our log: pid 11524 had 6261 maps and 6255 unmaps (balanced) before failing, so the loaded-program limit was not reached through leaked mappings; the compile-count limit cannot be excluded (count `Start of compilation of network` per client pid, not logged with a pid in the default log).
- hollance/neural-engine https://github.com/hollance/neural-engine: README only fetched (compute-unit docs, "Apple isn't giving third-party developers any guidance"); no program-limit text read.

## 7. Q4: the CPU fallback (details in section 2)

Works as an API call, does not work as a fallback: accepted, not honoured for rev2/rev3 (same ANE executions), cold compile still happens (CPU-first 89 s / +82 s CPU; GPU-first 64 s / +55 s CPU; the default read after the CPU-first run was warm). During an ANE compile stall a CPU/GPU-forced rev3 request waits for the same compile. `.fast` (CPU-only by Apple's own list) is the real ANE-free rung.

## 8. Q5: recommendations, ranked

1. Cancel what you abandon (warm only). Evidence: cancel measured (section 2); the app abandons at 8 s without cancel (`TextRecognizer.swift:225-229`), and the abandoned `perform` keeps its place in the per-process queue. Cost: small (keep the `VNRecognizeTextRequest` so `deadline` can `cancel()` it on Timeout). Risk: Cancelling a request that waits for a cold compile may restart the compile (ane-ocr-stall.md); so cancel only after the first answer (`warm == true`, the 8 s regime), keep the 90 s never-cancel for the cold phase. Unmeasured: cancel during a cold compile (probe in section 0.6).
2. One Vision text request in flight per process, latest frame wins, and start the 8 s clock when the request starts executing, not when it is queued. Evidence: serialization (section 2: 3.7-4.0 reads/s from 1 to 16 threads, latency = N x 0.25 s); DTS also advises fewer parallel requests; a queue wait counted as "did not answer" makes `OCRHealth` call a healthy rev3 stalled (`OCRHealth.lateAfter = 8`). Cost: a small gate (serial actor / AsyncSemaphore) in `TextRecognizer`; risk: low. Utilisation rule: at 0.37 reads/s (the user's app) a queue is stable only while the mean read is < 2.7 s; measure the app's read-time histogram (a 175-line page is 0.65-0.88 s).
3. Isolate the accurate reads in a helper process (XPC service in the bundle, sandbox-safe in the sense that bundled XPC services are normal MAS practice; not tested here) with a supervisor that can kill and restart it. Evidence: per-process lock (two processes do not slow each other; one process in a 138 s cold compile did not slow the other), pid 11524's 3 h Code 13 state that only a restart cured, forum 840559 (reboot only). Cost: large (an earlier round, ocr-iso, did something like it for the Swift models); risk: a kill mid-compile restarts the compile, so kill only after the helper has answered once and has not answered for N s; warm-up cost is per binary, so the helper gets its own 60-140 s first compile (fix the helper's path/bundle id forever).
4. Detect the persistent Code 13 state and recover by restarting the process or helper, not by waiting. Evidence: 13,361 errors in 2 h 57 min in one pid; 98 errors in the earlier 10-17 incident; `OCRHealth.notReadyRetryEvery = 5` keeps asking forever. Rule candidate: N consecutive Code 13 over more than 2-3 minutes on a process that had answered before -> restart helper (or tell the user to relaunch). Cost small if (3) exists, medium otherwise.
5. Keep `.fast` as the last rung and say Latin only; do not add a CPU/GPU rung for rev3 (measured useless).
6. Keep the binary path/bundle id stable and never copy the helper; warm-up (60-140 s, one width class each) at launch is right; check free disk first (ANECompilerService failed with `No space left on device` 27 times in this Mac's log; failed compiles are not cached and retry every ~33 s).
7. Do not bother with request/handler reuse, `preferBackgroundProcessing` (not measured; Apple says it trades latency for resource burden) or `VNSequenceRequestHandler` (tracking only).
8. Possible, unmeasured: reduce per-read work (smaller `regionOfInterest`, `minimumTextHeight` > 0, `usesLanguageCorrection = false` for the paragraph probe): the read is host-CPU-bound (~0.2 s fixed + ~2.6 ms per line), so these shorten the queue directly.
