## 1. Prompt design
- Few-shot by similarity (TM-RAG). Agrawal et al., https://arxiv.org/abs/2212.02437 [V]: "1-shot noisy unrelated example can have a catastrophic impact on output quality." and "Adding similar examples based on an n-gram overlap with the test source significantly and consistently improves" (S: beats kNN-MT on 2 of 4 out-of-domain sets). Moslem et al., https://arxiv.org/abs/2301.13294 [V]: "the translation quality with few-shot in-context learning can surpass that of strong encoder-decoder MT systems"; fuzzy matches (embedding-retrieved TM pairs) combined with NMT output "can further improve translation quality", most for less-supported languages; pairs EN->AR/ZH/FR/RW/ES (no ja/ko, no source-side zh/ja). No numbers on the abstract page; Slator says gains flatten as examples grow [S].
  - Cost: +100-400 prompt tokens per call (3-5 examples); latency ~+0-100 ms (prefill only); no extra calls. Fit: GOOD. Mwoyeo already holds a source->translation memory; fuzzy retrieval from it is the natural TM-RAG. Caution from Agrawal: a bad (unrelated) example is worse than none, so use a similarity threshold, and use same-app/session pairs only.
- Domain/register/persona: no controlled number found in this round [U]. Translation-agent uses "You are an expert linguist, specializing in translation from {source_lang} to {target_lang}." (https://raw.githubusercontent.com/andrewyng/translation-agent/main/src/translation_agent/utils.py ~line 86 [V]). Treat persona as free and unmeasured; a one-line "this is a chat message / game UI" hint is cheap and testable.
- Structured JSON with ids and batch size: no controlled study found. Only anecdote: LLMTranslate 0.3.0 changed the parser "to map translations using an item number the model returns, after an earlier bug offset translations by one row" (https://cran.r-project.org/web/packages/LLMTranslate/news/news.html [S]); custom.mt recommends up to 25 segments per request, larger adds latency (https://custom-mt.atlassian.net/wiki/spaces/CD/pages/516816897/ [S]). Mwoyeo's "one translation per line in order" has the same offset risk: ids + count check are cheap insurance. Batch size is an open measurement for the bench.

## 2. Knowledge-augmented prompting
- MAPS (Exploring Human-Like Translation Strategy), https://arxiv.org/abs/2305.04118 [V]: "Both automatic (3 LLMs x 11 directions x 2 automatic metrics)" and "human evaluation (preference study and MQM) demonstrate the effectiveness of MAPS." Pipeline: LLM extracts keywords, topic, demonstrations, translates with each, then selects. Numbers not on the abstract page. Cost: 3-5 calls plus a selection call (~4-6x), latency 3-4 sequential steps (>2 s). Fit: POOR for the lens; the useful idea (keyword/term knowledge) can be done offline in the background.
- Glossary in prompt: WMT23 terminology study (https://arxiv.org/abs/2310.14451 [S]): prior work found glossary prompting "generally effective in increasing the number of terms used". WMT25 Lingua Custodi (https://arxiv.org/pdf/2510.17504 [S]): constraint-prompting "can typically satisfy most of the constraints but suffer from high computational cost and sometimes low translation quality" (it forces terms even if the sentence goes wrong). Fit: GOOD at tiny cost; only inject entries whose source term occurs in the batch (Mwoyeo already does glossary pairs). Do not inject the whole glossary.
- DiPMT, Ghazvininejad et al., https://arxiv.org/abs/2302.07856 [S]: dictionary entries for some input words as hints; "English-to-Tagalog rises from 25.5 to 41.3" (S, low-resource). Gain is for rare/low-resource words; for ja/zh/ko<->en with modern LLMs, expected small [U]. Cost: tokens only. Fit: only for game/domain terms, same mechanism as glossary.

## 3. Multi-step and agentic pipelines
- translate -> reflect -> improve (Ng translation-agent), https://github.com/andrewyng/translation-agent [V]: README: "Prompt an LLM to translate a text from `source_language` to `target_language`;" "Have the LLM reflect on the translation to come up with constructive suggestions for improving it;" "Use the suggestions to improve the translation." Caveats: "sometimes competitive with, but also sometimes worse than, leading commercial offerings"; traditional models "often faster/cheaper to run than our approach here". Code: utils.py default model gpt-4-turbo ~l.22, temperature 0.3 ~l.23, MAX_TOKENS_PER_CHUNK=1000 ~l.14 (line numbers approximate, from fetch tool). 3 sequential calls: ~3x calls, ~3-4x latency, ~4x tokens (reflect+improve re-send source+draft).
- TEaR (Translate, Estimate, Refine), Feng et al., https://arxiv.org/html/2402.16379v3 [V]: Zh-En WMT23 sample (200 segs), few-shot initial vs TEaR: GPT-3.5-turbo COMET 78.67->79.50 (+0.83), Gemini-Pro 77.87->78.47 (+0.60), Claude-2 66.47->74.69 (+8.22), while BLEU moved -0.34/-2.33/+0.65. Paper: iterating refinement reduced performance, one round best (Appendix D). No ko; ja only human preference. Cost not reported: 1 translate + 1 estimate + refine only for flagged segments (94 of 200 flagged for GPT-3.5). Reading: big gain only for the weak model (Claude-2); +0.6-0.8 COMET for stronger ones. Takeaway: refinement helps weak drafts; refine only when the estimator flags.
- Self-Refine, https://arxiv.org/abs/2303.17651 [S]: "~20% absolute improvement on average in task performance" across 7 tasks (not translation-specific; translation not among them as far as the snippet shows [U]).
- LLMs as post-editors: Raunak et al., https://arxiv.org/abs/2305.14878 [V]: GPT-4 post-edits are "meaningful and trustworthy" yet the authors warn it "could produce hallucinated edits". WMT25 QE-informed retranslation, https://arxiv.org/html/2511.13884v1 [V]: "APE systems are still known to overcorrect the output of Machine Translation (MT), leading to a degradation in performance."; their winner is retranslation/selection, avg dCOMET +0.0201, while masked correction was -0.0108. Li/Ji/Tiedemann https://arxiv.org/abs/2510.06471 (via ctx-B [V]): test-time scaling "proves highly effective in a post-editing context" but only with domain tuning. So: post-editing helps when drafts are bad, hurts when they are good (overcorrection); gate it.
- Step-by-step (research, draft, refine, proofread), Briakou et al. (Google), https://arxiv.org/html/2409.06790v1 [V]: Gemini 1.5 Pro, MetricX-23 reference-based, WMT24 9 langs: zero-shot 3.04 -> full 2.20 (-0.84); en-zh 3.65 -> 2.75, en-ja 2.60 -> 1.73, en-de 1.98 -> 1.27; research+draft 3.04->2.58, refine ->2.24, proofread ->2.20 (only ~-0.04). Docs up to 250 tokens. "simply drafting without research yields only small and non-significant improvements or even regressions". Segment-level baselines trail by >0.7 MetricX. Cost not reported (4+ calls, proofread in a new conversation). Counter-evidence, https://arxiv.org/abs/2506.04521 [V]: "we find no clear evidence that performance gains stem from explicitly decomposing the translation process via CoT, at least for the models on test"; "prompting LLMs to 'translate again' and self-refine yields even better results than human-like step-by-step prompting". Evidence is for paragraph-length docs, not 5-20 token lines.
- TransAgents (multi-agent, literary), https://arxiv.org/html/2405.11804v1 [S]: preferred by humans/LLMs over human references despite lower d-BLEU; "underperform in contemporary domains" (S); all agents GPT-4; ultra-long literary text. Fit: NO (cost and latency orders of magnitude over budget).
- DelTA, https://arxiv.org/abs/2410.08143 [S]: memory of proper nouns, bilingual summary, long/short-term memory; sentence-by-sentence; "Consistency scores rose by up to 4.58 points and COMET scores by up to 3.16 points on average" (S). Fit: the proper-noun record + summary idea maps to Mwoyeo's term memory; the extra LLM calls to update memory should run in the background (see ctx-B on context).
- Short segments / budget: no source shows these pipelines winning on 5-20 token UI lines; all numbers are doc-level (>=130 tokens) or 200-segment WMT samples. Latency multiple 3-4x puts a 2-call refine at ~2-6 s on cloud. Fit for the lens: NO as default; YES as a background upgrade (section 8) for text the user keeps reading.

## 4. Hybrid NMT + LLM, QE-gated routing
- Google's own doc, https://docs.cloud.google.com/vertex-ai/generative-ai/docs/translate/translate-text [V]: NMT "Fastest Real Time Translation", "Low latency, suitable for chat and real-time applications."; Translation LLM "Highest quality translation. Outperforms NMT and Gemini 2.5 Pro in quality." "Latency is still slower than NMT."; it is "far more likely to significantly rewrite a sentence to make it sound more natural". (A search snippet adds NMT ~100 ms and 3x/20x vs Gemini 2.0 Flash [S].) Product precedent for choosing per use case, not for automatic routing.
- QE-gated: WMT25 paper above [V]: gating by COMET-style QE x: x>=0.90 no edit; 0.50<x<0.90 mask minor spans; x<=0.50 mask all error spans; goal a "Gain-to-Edit ratio". JobResQA (https://arxiv.org/pdf/2601.23183 [S]): selective post-editing gave COMETKiwi +0.05..+0.45 (not comparable). Weakness: QE rankings often disagree with reference-based ranking (https://arxiv.org/pdf/2603.04083 [S]). COMET-Kiwi runs on GPU/CPU ~100s of ms and is a ~2 GB model [U]; on a Mac app it is a heavy dependency. Cheaper gate: an LLM-free heuristic (OCR confidence, length, Apple-vs-LLM disagreement, glossary hit) [idea, no source].
- Unbabel routing: no source found [unverified]. Evidence that selection by a metric works is in section 5.
- Fit: the cheap form of hybrid is what Mwoyeo can do now: Apple Translation draft shown at once, LLM only where the user lingers (see 8).

## 5. Candidate selection
- Quality-aware decoding with Tower, https://arxiv.org/pdf/2510.06866 [S]: "greedy ... COMET 84.7 -> 88.9 and BLEU 34.4 -> 52.7" with MBR over 50 nucleus samples (Tower, doc-level, 0 context; the BLEU jump looks odd, check before citing). WMT24 Unbabel: MBR beat tuned reranking on Tower-V2 70B (https://aclanthology.org/2024.wmt-1.12.pdf [S]). Farinhas et al., https://aclanthology.org/2023.emnlp-main.733 [S]: MBR "very effective" with few samples. Combine/QE-rerank: higher temperature helps candidate diversity but too high hurts (https://arxiv.org/pdf/2401.06688 [S]). QE rerank at doc level: BLEURT-20 +2.00 with 2 candidates, +5.09 with 32 (https://aamt.info/?p=1087 [S]).
- Cost: N parallel calls (N=4-8: 4-8x tokens, latency ~1x if parallel) plus a metric run (COMET quadratic for MBR). Fit: POOR in a 1-2 s lens (cost, rate limits); possible for cache-warming/background only. Cheaper analogue: 2 engines in parallel (Apple + LLM) and pick by cheap rule.

## 6. Noisy input
- No direct evidence found for "translate OCR text and repair OCR errors in one call". Closest: OCR post-correction work (HIPE-OCRepair frames LLM repair as text-only with a duty to avoid adding content, https://arxiv.org/pdf/2607.08143 [S]; a ByT5 corrector helped only the OCR engine it was trained on, https://arxiv.org/pdf/2606.29213 [S]). Caution is consistent with hallucinated edits (2305.14878 above). Practical, [idea, no source]: one prompt line "the text comes from OCR; fix obvious character errors silently, never invent words" and measure on the bench with injected ja/zh confusions; keep Vision confidence as the gate.
- Partial text / incremental: streaming-MT literature uses re-translation and flags flicker. Zoom group's SSBD, https://arxiv.org/html/2509.21740v2 [S]: "up to 1.7x speedup over standard autoregressive re-translation" and an earlier version "80% reduction in flickering" from a display-only mask-k of unstable suffix. LLM SimulMT (https://arxiv.org/html/2309.06706v3 [S]) needs fine-tuning. For screen text: wait a short settle (lines unchanged for N ms, or a trailing punctuation/complete-sentence check) before the LLM call; translate partial text only with Apple (cheap). Mask-k analogue: do not replace a shown line when the new source differs only in the last few characters.

## 7. Model and decoding
- Temperature: DeepSeek-R1 on Flores-200 0.0-1.0 (https://arxiv.org/pdf/2502.11544 [S]): lower "more stable and accurate", best varies by pair, worst ~0.6 for en-zh/en-de. Higher only for multi-candidate. Mwoyeo temp 0 is fine.
- Reasoning: ctx-B cites Rajaee & Kocmi https://arxiv.org/abs/2602.14763 [V] "explicit reasoning consistently degrades translation quality" and 2510.06471 "consistently degrades translation quality" when forced. Large reasoning models also lag on terminology-heavy domains (https://arxiv.org/pdf/2505.19987 [S]: Zh=>En term accuracy ~52-53% typical, o3-mini 45.59%). Confirmed: keep thinking off. Refinement: reasoning helps only in a post-editing/test-time-scaling setup with tuning, i.e. not the lens.
- Dedicated translation LLMs (all authors' own claims, [V] abstracts): TranslateGemma, https://arxiv.org/abs/2601.09012: "Automatic metrics show consistent and substantial gains over the baseline Gemma 3 models across all sizes." "Notably, smaller TranslateGemma models often achieve performance comparable to larger baseline models" (4B/12B/27B; MetricX tables not extractable: the PDF was fetched but not kept). Tower, https://arxiv.org/abs/2402.17733: "surpasses open alternatives on several tasks relevant to translation workflows"; Tower covers few CJK pairs [U]; Tower70B en-ja MetricX 2.16 vs Gemini step-by-step 1.73 (Briakou Table 5, above). Seed-X, https://arxiv.org/abs/2507.13618: 7B, 28 languages, "achieves performance comparable to leading closed-source models, including Gemini-2.5 and GPT-4o". Hunyuan-MT, https://arxiv.org/abs/2509.05209: 7B, 33 languages, "ranking first in 30 out of 31 language pairs" at WMT2025 (the ranking is against WMT25 systems, not a general mini-LLM check). Sakura (ja->zh): not verified, no source fetched.
- Whether a small model beats a frontier mini on ja/zh/ko<->en/ko for screen text: NO head-to-head evidence found; only author claims on WMT-style text. Needs the bench.
- Local on Apple silicon, https://omlx.ai/benchmarks/vf1p6vwd and siblings [S]: HY-MT1.5 1.8B 115 tok/s on M3 Max (4k ctx), ~105 tok/s M4 Pro, ~40 tok/s M2 8 GB; 7B 4-bit 92 tok/s M5 Max; community numbers. A 15-token line is ~25 output tokens: ~0.25 s decode at 100 tok/s plus prefill, so a 1.8B-7B local MT model fits 1-2 s on M-Pro/Max, not safely on an 8 GB base machine. Memory 1-5 GB: matters for the footprint audit.

## 8. Progressive display
- Precedent: Google "Translation LLM" vs NMT split is by latency tier (doc above); the retranslation literature (SSBD above) is the closest research on revising shown text. I found no paper or product doc showing "NMT first, replace with LLM" for screen translation [unverified]. This is a design inference.
- UX cautions (inference + SSBD flicker evidence): replace only once per line; do not replace while the user's gaze/selection is on it (hover, selection, scroll in progress); keep line length/layout stable (overlay boxes); replace silently if the edit is small and mark visibly only if changed meaning; never replace after the user copied it; cache the LLM result so the second view is instant. LLM "far more likely to significantly rewrite", so a swap may change the sentence the user was reading.

## 9. Synthesis: ranked, with the 3 first experiments
Gain figures are expectations, not measurements except where cited.
1. Fuzzy TM few-shot from the app's own memory (+ glossary hits only). Gain: consistency of names/terms and register; literature supports similarity-selected examples (2212.02437, 2301.13294) but gives no ja/ko numbers. Cost: +100-400 prompt tokens, 1x calls, +~0-100 ms. Size: small (retrieval over existing memory; similarity threshold; same-session pairs). Measure: bench with recurring-term test set, term-consistency rate and COMET/MetricX-QE, vs the current prompt.
2. Progressive display (Apple draft at once, LLM replaces once, only if the lens stays on it). Gain: perceived latency ~0 s vs 1-2 s; quality = LLM. Cost: 1 LLM call, same as now, no more. Size: medium (state machine for replace policy). Measure: time-to-first-text, replacement count per session, % of replaced lines the user was looking at (local only, no telemetry; use the render harness), plus a flicker metric as in SSBD.
3. Prompt/format hygiene: item ids + count check, a one-line screen-text hint ("OCR text, may contain recognition errors; fix obvious ones silently, never add words"), batch-size sweep (1/3/8/16 lines), settle-before-translate for partial lines. Gain: fewer misalignments/omissions, some OCR robustness; no source gives numbers, so it is a measurement. Cost: near zero. Size: small. Measure: alignment-error and omission rate on noisy OCR fixtures with injected errors.
4. Gated refine in background: a second LLM pass only for text that stays on screen or whose cheap gate fires (Apple-vs-LLM disagreement, low OCR confidence). Gain: TEaR +0.6..+0.8 COMET for good drafts, large only for weak ones; risk: overcorrection (2511.13884). Cost: +1-2 calls only on a minority. Size: medium. Measure: A/B quality plus fraction refined plus edit distance.
5. Local dedicated model (TranslateGemma/HY-MT/Seed-X class) as an offline engine. Gain: free, private, 0.3-1 s on M-Pro/Max; quality unproven vs a frontier mini on ja/zh/ko screen text. Cost: 1-5 GB RAM. Size: large. Measure: bench head-to-head first (not build first).
6. Not worth it for the lens: MAPS, TransAgents, multi-step research/draft/refine/proofread, MBR/best-of-n. Cost 4-50x, doc-level evidence only.
Bench, one rig for all: ja/zh/ko<->en/ko, 5-20 token lines and chat turns, with injected OCR noise, recurring-name sets; metrics MetricX-QE or COMET-Kiwi plus an LLM-judge pair (both orders) plus alignment/omission/term-consistency counters; temp 0, thinking off.
Gaps I could not close: MAPS/DelTA/TranslateGemma numbers (abstract pages only), Unbabel routing, Sakura, batch-size studies, OCR+MT evidence, any NMT-first progressive precedent.
