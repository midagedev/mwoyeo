Rules vs light learned judges on the translate / keep boundary: accuracy and speed, H2 train / H3 test (round m-bench, 2026-10-20)
==============================================================================================================================
Question  The user asked (2026-10-20) whether the keep decision is better made without a model (heuristics) or by a light model that may be faster and more accurate, and whether
          EmbeddingGemma is usable. Judge 1 is today's rules (TranslationFilter + InlineMath, OR CodeRegion = what the app does); judges 2-6 are learned: layout trees (LightGBM),
          a hashed char n-gram linear model, static embedding (potion-multilingual-128M), multilingual-e5-small and EmbeddingGemma 2 (text backbone) with a logistic regression,
          each alone and with the layout features. Round k3b will change the rules: `mbench/run.sh rules` re-runs judge 1 on any tree (needs only python3 + numpy + PIL).
Data      Pictures and Vision reads are fixed (H2 /tmp/k3a/wb, H3 /tmp/h3/legA, cases + papers /tmp/l0/g4b-work): no Vision was run. Scratch /tmp/m-bench; nothing but scripts and this file is in the repo.
Split     Fit pool = H2 + the 12 code cases + the two CC BY papers; 6-fold GroupKFold, the group = scene (H2) / case (code) / paper (papers). Hyper-parameters (C, tree size) = lowest
          out-of-fold log loss; thresholds = out-of-fold predictions of the dev-screen rows (H2 + code). H3 enters only as the final prediction (check C2). The H2 rows below are
          out-of-fold; the thresholds were also read off them, so they are slightly optimistic.
Inputs    Allowed only (addendum A1.4): block id / text / rect / read / lang, the word boxes of *.ocr.jsonl, the png pixels (tint, chip backgrounds), the regionfeed record. No units.json, no
          label field (reason stats unc scene look region) as a feature; `look` and `scene` are never features (check C3). Training drops either / none words and no-letter blocks as the scorer does.
Scorer    ONE scorer: every judge is written as keeprules-format records {id, needs, spans} and scored by rules_report.accumulate (the code behind RESULTS-h2 / RESULTS-code-region):
          a word is kept when its block is kept whole or a span covers it (A1.1). The same records go through the unchanged h2_report.py (check C5; run-h3.sh's rename of H3 to `h2` is
          why that tool's headings read "H2" for H3 numbers). Reproduction before anything else was scored:
            REPRODUCTION (RESULTS-h2-2026-10-20.txt: rules OR CodeRegion, doc read, tp 3281 fp 65 fn 945, P 0.98 R 0.78): got tp 3281 fp 65 fn 945 -> MATCH
          and run-h3.sh (unchanged, H3_WORK=/tmp/h3/legA) on the same H3 records: doc rules only tp 5255 fp 81 fn 4192, rules OR CodeRegion tp 6281 fp 90 fn 3166 (= the "BOTH" rows below).
Tasks     block   keep the whole block (needs=false), binary; a labelled-mixed block kept whole counts as translate->kept for every judge (A1.2); `mixed kept` is in the table.
          inline  every scored word of every block (needs=true everywhere, spans = the words the judge keeps): the universe is identical for all judges (A1.1); the right-hand
                  columns repeat it for words of blocks that hold a translate word (the real "inline pieces in prose").
          both    block judge + word judge in the translated blocks;  hybrid  the rules OR CodeRegion decide the block, the judge's word model protects spans in the rest.
Points    F1 = threshold with the best out-of-fold F1; P98 = the most keeping threshold whose out-of-fold precision is >= 0.98 (block precision for the block judge, word precision for the
          word judge). On H3 the P98 points land at block P 0.88-0.95 / word P 0.91-0.97: the precision does not carry over from H2 to the new looks.

ANSWER (H3 = test; doc read unless said; word counts: 9447 keep words, 7302 translate words; 1254 keep blocks)
  1. Block task (keep the whole block): no winner. Rules OR CodeRegion P 0.96 R 0.89 F1 0.92 (vn 0.92); best learned gbt-nopix @P98 P 0.94 R 0.92 F1 0.93 (vn 0.89), @F1 P 0.91 R 0.96 F1 0.94
     (vn 0.89). Differences of +-0.03 on 1254 keep blocks are inside the noise, the learned judge keeps 228 translate words (rules: 89) and wrongly whole-keeps more mixed blocks (54 of 160 vs 34).
     The learned judges win only in English looks (block F1 en: rules 0.74, gbt-nopix 0.82-0.87); they lose precision elsewhere. Text-only judges are weak here (recall at the P98 point:
     n-gram 0.68, potion 0.25, e5 0.55, EG2 0.59); with the layout columns they reach 0.89-0.91 F1, below the trees.
  2. Inline / word task: the learned word judges win by a wide margin. Rules' spans alone: word R 0.05 (span F1 0.07). gbt-nopix: word P 0.95 R 0.99 F1 0.97, span exact F1 0.88;
     on the words of blocks that hold translate words R 0.99 (rules 0.00). As a pipeline (rules decide the block, the word model protects spans: HYBRID) gbt-nopix @P98 gives
     word P 0.95 R 0.99 (fn 62 of 9447) against rules P 0.99 R 0.66 (fn 3166). The price: translate words kept 538 of 7302 (7.4 %) against 90 (1.2 %); 444 of the 538 (83 %) are in ja / zh-Hans reads
     (where the doc read cuts Latin runs into single characters) and 336 (62 %) in mixed blocks. Even the cheapest learned word model helps in the hybrid: n-gram @P98 P 0.96 R 0.96, e5 @P98 P 0.96 R 0.97.
  3. By reason (gbt BOTH @P98 vs rules OR CodeRegion, keep-word recall): log 1.00 vs 0.21, url 1.00 vs 0.04, id 1.00 vs 0.34, cmd 0.99 vs 0.34, path 1.00 vs 0.48, config 0.99 vs 0.71,
     code 1.00 vs 0.95. Block-weighted url recall (1841 url words, ja / zh-Hans reads cut them per character): rules 0.59 overall = ko 0.79, ja 0.04, en 1.00, zh-Hans 0.52; the learned judges with layout 1.00. Per language (BOTH): rules ko word R 0.95 / ja 0.59 / en 0.69 / zh-Hans 0.59 against gbt-nopix 1.00 / 1.00 / 0.95 / 1.00 at P 0.98 / 0.93 / 0.97 / 0.93.
  4. The winner is the smallest model: LightGBM on layout features, 400 + 400 trees = 2.1 MB of model text, 0.8 ms per block and 0.4 ms per word with batch=1 in Python (tint read off the pixels
     included), 397 MB RSS of which 217 MB is the python + torch import; the Swift rules cost 0.03 ms (filter + spans) + 3.1 ms (CodeRegion, per block) + 1.2 ms (regionfeed tint, includes PNG decode) = 4.3 ms per block
     (second pass at another load: CodeRegion 5.6, regionfeed 2.5). Every timing is under a load average of 50-300 on 10 cores (uptime recorded per judge) and is a Python upper bound for a Swift port.
     `gbt-nopix` (OCR text + word boxes only, no pixel feature) is as good as `gbt`: the pixel features (tint, chip background) are not what carries H3 (check the importances: block tint
     luminance was the top gain of `gbt` (29 % of the block model's gain), and leaving every pixel feature out costs nothing on H3).
  5. Embeddings do not pay for themselves. e5-small + layout block F1 0.91 @P98, word P 0.95 R 0.96 (13-14 ms per block b=1, 4.9 batched, 7 ms per word, 1.07 GB RSS); EmbeddingGemma 2 + layout
     0.90 / P 0.95 R 0.94 (80 ms per block b=1, 28 batched, 40 ms per word, 2.0 GB RSS, 1084 MB fp32 weights); potion + layout 0.89 / 0.94 / 0.94 (0.7 ms, 512 MB table). EG2 is not better than e5 or
     potion here, and Matryoshka cuts lose recall at the P98 point (EG2 768 -> 256 -> 128 dims: block R 0.59 -> 0.38 -> 0.32). torch dynamic int8 is SLOWER than fp32 on this CPU (e5 14.5 vs 10.9 ms
     per text b=1, batched 20 vs 4.3; EG2 109 vs 87, batched 165 vs 35) and its accuracy is unchanged for e5 (block F1 0.83 vs 0.82 @F1); the EG2 int8 judge was not trained (its embeddings ran at
     ~3 strings/s, stopped at 2048 of 4278 block texts).
  6. Caveat that decides how far to trust this: H3 is a hold-out in content, scenes and looks, but it is drawn by the same generator as H2 (h2.py machinery): every inline piece of code is a
     monospaced chip, every code region has the generator's spacing. A learned judge can use the recipe; the rules cannot. The learned block judge falls from out-of-fold F1 0.97-0.99 (H2) to 0.93-0.94 (H3, new looks), the rules from 0.94 to 0.92.
     Before any shipping decision a hold-out of REAL screens (not drawn by h2.py) is needed; the P98 points did not hold their precision on H3 either (point 'Points' above).
  7. Core ML: LightGBM is not a coremltools source. An XGBoost classifier of the same size (400 trees, depth 5) on the same 111 block features converts (coremltools 9.0, 0.31 MB, 0.5 ms per call
     from Python) and agrees with XGBoost on 399 of 400 H3 blocks at 0.5 (max |dp| 0.024); the LightGBM trees are plain arrays (a ~60-line Swift evaluator would do). No accuracy was scored for the XGBoost twin.
