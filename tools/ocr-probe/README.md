# ocr-probe
Times one Vision text request, to tell a stalled recognizer from a slow one. Build `swiftc -O probe.swift -o probe`; run `./probe chat.png accurate [revision] [ja] [seconds]` (or `fast`, `accurate-cpu`: every stage on the CPU).
It prints the system's revisions and languages, then `lines=<n> <seconds>` or `no answer in <n> s` (default 40 s, exit 1).
Healthy Mac: revision 3 (the default, the only one that reads ja/ko) answers in ~30 s the first time (the models compile) and ~0.3 s after; revision 2 and `.fast` in under 0.3 s.
Stalled (2026-10-17): revision 3 never answers and `ANECompilerService` (root) spins at 60-99 % CPU, while revision 2 and `.fast` still answer.
Never kill `ANECompilerService` or a probe that is still loading: a client that goes away restarts the compile.

`healthy.sh` is the gate for the fallback ladder and the paragraph grouping (healthy read, `stall`/`stall-vn`/`slow:<ms>` fakes, ja notice, paragraphs of article.png and sub-mid.png). Run it with
`SP=<dir with in/chat.png, in/vn.png, in/article.png, in/sub-mid.png> NEW=<built Mwoyeo binary> MAIN=<baseline binary> OUT=<output dir> ./healthy.sh`.
2026-10-17 (ocr-vn): the app asks no Swift Vision request at all any more (`RecognizeTextRequest`, `RecognizeDocumentsRequest`), so the checks of the child warm-up (`--warm-vision`, `--assume-vision-ready`, `slow-child`, `fail-child`) and of the Swift path are gone, and `MWOYEO_FAKE_OCR=stall` stalls revision 3 like `stall-vn`.

`inprocess.swift` is the first measurement of a block that was blamed on "a pending Swift request": in ONE process it starts a Swift `RecognizeDocumentsRequest`, then runs a `VNRecognizeTextRequest` 2 s later. While the document model was loading, accurate revision 3 blocked for more than 60 s and revision 2 for more than 30 s (`.fast` answered in 0.12 s). Build `swiftc -O inprocess.swift -o inprocess`; run `./inprocess chat.png rev3|rev2|fast [seconds]`.
2026-10-18 (vision-revive): that block was a cold compile in the system's ANE service, not a property of Swift requests. `mix.swift` measured it warm: 30 looped document requests beside 10 concurrent revision 3 reads left those reads at 0.16-0.27 s (a warm document read 0.33-0.48 s, a warm `RecognizeTextRequest` 0.27-0.58 s). Cold (a binary's first run) revision 3 alone takes 65-119 s, the document model 82-87 s, a text request 32 s, queued one after another; revision 2 and `.fast` answer in under 0.25 s throughout; models load per language. A cold Swift text model (ar) with revision 3 warm kept a revision 3 read at 37 s, so the app reads through revision 2 / `.fast` while a Swift step compiles. The app now loads the Swift models itself at every launch (`SwiftVisionGate`, `TextRecognizer.warmUp`) and reads paragraphs with `RecognizeDocumentsRequest` once its model is loaded, else through revision 3 + `ParagraphGrouper`. `mix.swift` header: usage. To make a cold cache for a gate, change the app's bundle identifier in a copy of the .app and re-sign it (the cache is keyed by it); a rebuilt or re-signed binary with the same identifier stays warm.

2026-10-18 (first-run): `relaunch-cold.sh` measures whether a relaunch during the cold revision 3 compile starts it over. It does: on a fresh bundle identifier the compile took 64.3 s uninterrupted, and 62.0 s for a relaunch 30 s after a kill (a continued compile would have taken about 34 s); the script itself, run again: 64.0 s and 62.8 s. So the permission restart of a new user's first two minutes costs the whole compile again, unless the warm-up starts after Screen Recording is granted. `APP=<built Mwoyeo.app> bash relaunch-cold.sh`.

2026-10-18 (r3-docs-xpc): documents are read only by the Docs service (`MwoyeoReader-docs.xpc`, `App/Reader/DocsHost.swift`); the app binary has no `RecognizeDocumentsRequest` (`nm -u Mwoyeo | grep -c RecognizeDocuments` is 0), and the child warm-up (`--warm-vision`, `SwiftVisionChild`) and the `RecognizeTextRequest` step are gone. A pass that wants the document layout sends the read when Docs is idle and warm for the key, waits S = 2 s, and reads with VN + `ParagraphGrouper` (v1.1.0 quality) from then on while the request runs to completion, never cancelled; when it answers, the lenses that stood in re-read once. Nothing waits for Docs, so a cold figure page cannot silence a lens.
`reader-cold.sh [p13]` is the decisive test. Failure mode: a document read compiles in the GUI process, or a lens goes silent behind it. It builds the app AND its services with a fresh bundle id (`xcodebuild … MWOYEO_APP_ID=<id>`, so `<id>`, `<id>.reader.lines`, `<id>.reader.docs`, each with an empty e5rt cache under `~/Library/Caches/<that id>/`), warms revision 3 in the GUI and the document model in the Docs service on the drawn probe picture (what a user has after the first launch; it does not compile the networks of a figure page), then renders the page with `--mode adaptive --then reader-ready,again` and asserts: `silence: longest ≤ 8000`, the GUI's cache gains no entry, the Docs service's cache does (the script prints where), `reader-ready` comes, the first pass is VN and a later pass is a document read, `drain: in-flight=0`, no new `.tmp`. `SRC=<tree>` points it at another tree: on a tree where documents are read in the GUI it prints FAIL silence (~90 s). `MWOYEO_DOCS_WAIT=1` is the mutation of the silence gates (the pass waits for Docs, as the in-process path did).
`MWOYEO_FAKE_READER=docs-slow:<ms>` (every Docs job sleeps) shows the patience. With `--warm` the warm-up takes the sleep, then the lens's request is suspect after S = 2 s and the pass reads with VN (`silence: longest` ≈ 2.5 s on p13); the first late answer ends in a recovery re-read at once, and a Docs that keeps answering past S rests 1, 2, 4 … 30 s before each next request (`reader: docs … suspects=N late=N rereads=N slow-streak=N`), so a Docs that always answers past S is not asked by every re-read for ever. Without `--warm` the first pass finds Docs cold or warming and reads with VN at once (`fallbacks=cold:N`). `MWOYEO_FAKE_READER=crash:docs` kills the service on its first job (the warm-up): the render finishes with VN, the warm-up asks again after `Backoff.workerRestart` and relaunches the service (launchd waits ~10 s), `reader-ready` follows. `trace-render.sh <binary> [page]` renders with the trace on and must exit 0 (p6 with `MWOYEO_OCR_PATH=vn` ended rc=133 on `Int(CGRect.null.minX)` in a trace line).

2026-10-19 (r3a-host-lines): Lines are read by the Lines service by default, and both services belong to one actor, `App/Reader/RecognitionHost.swift` (it replaced `DocsHost.swift`): `ReadRouter`/`ReadScheduler` (one read in flight per worker, latest wins per client), a `WorkerHealth` per role, a `ReadWait` per pipeline (the lens's hint, `LensSignals.recognition`), `ReaderWarmup` (Lines first, then Docs, nothing for a new key while a lens is on), a 64-entry debug ring (`MWOYEO_READER_RING=1` prints it with the `reader:` lines) and the `reader` log category. `TextRecognizer` is a facade over it. A pass that no reader can take gets `.unavailable(why)` at once (the S of the kind passed, or a worker that is warming or restarting) and reads again on `readerReady`, never on a timer. `MWOYEO_READER=inproc` runs the Lines kinds in the app process (the equal gate's baseline and A/B); it is never the default. `MWOYEO_FAKE_OCR` and the in-process ladder are gone with it: use `MWOYEO_FAKE_READER=lines-slow|lines-e5rt|crash` (`healthy.sh` still names the old counters until R3c rewrites it). `reader-cold.sh` now asserts that the GUI's e5rt cache has no entry from the fresh id on (text and document networks both) and that the Lines service's cache gains entries; `reader-cold.sh ja` is the ja variant (`hint: preparingRecognition` within 3500 ms, silence <= 8000 ms). `MWOYEO_DOCS_WAIT=1` stays the mutation of the silence gates; `MWOYEO_READER=inproc` is the FAIL-first of the GUI cache gate.
